# Deploying to Vercel

## Prerequisites

- A Vercel account connected to this GitHub repo.
- The Supabase project fully migrated — all files in `supabase/migrations/`
  (through `20260813000015_answer_key_rls_hardening.sql`) applied via the
  Supabase SQL Editor, in order.
- A Gemini API key ([aistudio.google.com/apikey](https://aistudio.google.com/apikey)).

## 1. Import the project in Vercel

- New Project → import from GitHub → select this repo.
- Framework preset: Next.js (auto-detected, no `vercel.json` needed).
- Production branch: point Vercel's Production Branch setting at whichever
  branch you want live. This app was built on
  `claude/teacher-academy-blueprint-6br9ct` — merge it into `main` first if
  `main` is meant to be production, or set Vercel's Production Branch to
  this branch directly.

## 2. Environment variables

Project Settings → Environment Variables. Set these for Production (and
Preview too, if preview deploys should work against the same Supabase
project):

| Name | Where to find it | Notes |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Project Settings → API | Public, safe in the browser bundle |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | same page | Public, safe in the browser bundle |
| `SUPABASE_SERVICE_ROLE_KEY` | same page | **Server-only** — bypasses RLS. Never prefix with `NEXT_PUBLIC_`. Used only by `src/lib/supabase/service-role.ts` for the handful of reads that need it (see migration 15) |
| `GEMINI_API_KEY` | aistudio.google.com/apikey | Server-only, used by `src/lib/ai/` |

## 3. Supabase Auth URL configuration

Supabase Dashboard → Authentication → URL Configuration:

- **Site URL**: your production URL (e.g. `https://your-app.vercel.app`, or
  a custom domain once attached).
- **Redirect URLs**: add `https://your-app.vercel.app/auth/confirm` (and the
  same path on any other domain — custom domain, preview deploys — you
  expect signup/password-reset emails to work on).

`src/lib/auth/origin.ts` derives the origin from the incoming request
rather than a hardcoded env var, so email links work on any domain — but
only once Supabase itself is told that domain is allowed to redirect to.
Skipping this step means confirmation/reset emails will link back to the
wrong origin.

## 4. Deploy

Push (or merge) to the branch Vercel is watching — it builds and deploys
automatically. Check the build log is clean; it runs the same
`lint` → `build` → `typecheck` sequence as `.github/workflows/ci.yml`.

## 5. Post-deploy smoke test

- [ ] Landing page loads.
- [ ] Sign up with a real email, confirm via the email link, land on `/dashboard`.
- [ ] Promote your own account to admin via the Supabase SQL editor:
      `update profiles set role = 'admin' where id = '<your-user-uuid>';`
      then confirm `/admin` is reachable.
- [ ] Create a course → unit → lesson → activity, publish each, complete the
      lesson as a learner.
- [ ] Placement flow runs end to end and produces a level.
- [ ] Writing / speaking / role-play activities return real Gemini feedback.
- [ ] `/admin/analytics` shows the events generated by this smoke test.

## Notes

- Rotating `SUPABASE_SERVICE_ROLE_KEY` or `GEMINI_API_KEY`: update the value
  in Vercel's env vars and redeploy — changing an env var alone doesn't
  affect an already-running deployment.
- No background jobs or cron are used anywhere in this app; every route is
  request-driven, so no extra Vercel configuration (cron, edge config,
  etc.) is required beyond the environment variables above.
